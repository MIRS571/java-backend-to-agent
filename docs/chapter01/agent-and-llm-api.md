# 第 1 章：Agent、LLM API、消息、上下文与模型局限

> 本章状态：内容完成。验证日期：2026-09-02。示例仅使用 Python 标准库，不访问真实模型。

## 1. 本章解决的问题

学习 Agent 之前，必须先分清五个对象：**LLM、LLM API、Message、Context 和 Agent**。它们处于不同层次，却经常被混成“调用 AI”。

本章完成后，应当能够回答：

- 一次模型请求实际发送了什么；
- 为什么模型不会天然记住上一次 HTTP 请求；
- 普通模型调用与 Agent 的差别；
- 为什么模型输出不能直接当作订单、权限或交易事实；
- Java 后端和 Agent 服务各自应当负责什么。

## 2. 背景与技术动机

LLM（Large Language Model，大语言模型）的核心能力是：根据当前可见输入，生成后续内容。LLM API 则把这种能力包装成远程接口，让应用提交输入并接收输出。

一次 `用户问题 -> 模型文本` 只是**模型调用**，还不是完整 Agent。工程中的 Agent 通常还包含：

```text
Agent = 模型 + 指令 + 上下文 + 工具 + 状态 + 控制循环 + 安全边界
```

当任务只是分类、摘要或改写时，一次模型调用往往更简单、更便宜、更稳定。只有任务需要模型根据中间结果决定下一步、调用外部工具并循环推进时，才真正需要 Agent。增加 Agent 自主性通常也会增加延迟、成本和不可预测性。

## 3. 核心心智模型

### 3.1 模型不是业务系统

模型输出是根据输入生成的**候选结果**，不是数据库查询结果、权限判定或事务提交结果。即使文字非常肯定，也不能据此认定订单已付款、用户有退款权限，或某个写操作已经成功。

可靠的企业边界是：

- 模型负责理解自然语言、提出计划和生成候选参数；
- Java / Python 应用负责验证参数、查询真实数据、检查权限并执行操作；
- 数据库和业务服务负责保存确定性事实。

### 3.2 上下文不是记忆

**Context（上下文）**是本次生成过程中模型能够看到的信息，可能包括：

- 系统或开发者指令；
- 当前用户消息与选定的历史消息；
- 工具定义和工具返回值；
- RAG 检索到的文档片段；
- 输出格式要求。

上下文不是数据库，也不等于长期记忆。传统无状态请求需要应用重新发送历史；部分模型 API 支持通过响应 ID 或会话对象引用服务端状态，但仍然是应用显式选择并管理该状态，而不是模型在请求之间自行记住用户。

### 3.3 Agent 的关键是“循环与行动”

普通调用只有一次生成：

```text
输入 -> 模型 -> 输出
```

Agent 则可能重复执行：

```text
目标 -> 模型决定下一步 -> 应用执行工具 -> 返回观察结果
                    ^                         |
                    |---------继续或结束------|
```

真正调用数据库、HTTP API 或文件系统的是应用提供的工具代码，不是模型本身。模型通常只产生“希望调用哪个工具、传入哪些参数”的结构化请求。工具执行循环会在第 4 章实现，LangGraph 会在第 7 章把循环显式建模。

## 4. 输入、输出与执行流程

一次文本模型调用可以按以下顺序理解：

1. 应用取得用户输入，并从可信来源取得身份、租户和业务上下文。
2. 应用选择需要发送的指令、历史消息、检索资料和工具定义。
3. SDK 把这些对象序列化为 HTTP 请求，并携带鉴权信息。
4. 模型根据当前上下文生成一个或多个输出项。
5. SDK 把 HTTP 响应解析为消息、工具调用或结构化对象。
6. 应用验证输出，再决定返回用户、调用工具、重试、拒绝或继续下一轮。

下面是为了理解而简化的消息形式：

```json
{
  "model": "offline-demo-model",
  "messages": [
    {"role": "system", "content": "你是售后助手。"},
    {"role": "user", "content": "订单 A1001 已经发货了吗？"},
    {"role": "assistant", "content": "订单 A1001 当前状态：已发货。"},
    {"role": "user", "content": "那还能直接取消吗？"}
  ]
}
```

这是教学用的通用表示，不是所有厂商接口的固定协议。不同 API 可能使用 `messages`，也可能使用 `instructions`、`input`、content blocks 或会话引用。学习时应抓住“角色 + 内容 + 顺序 + 当前可见范围”，再查具体 SDK 的字段。

常见角色如下：

| 角色 | 表达的内容 | 不能承担的职责 |
| --- | --- | --- |
| `system` / `developer` | 产品规则、任务边界、输出要求 | 不能代替服务端权限控制 |
| `user` | 用户本轮请求或用户提供的信息 | 不能被默认视为可信业务事实 |
| `assistant` | 模型先前生成的消息 | 不能证明之前内容正确 |
| `tool` | 应用执行工具后的结果 | 仍需处理错误、过期数据和越权风险 |

不同 API 对角色名称和优先级的定义可能不同，以所用服务的官方文档为准。

## 5. 最小可运行示例

本章使用离线 `FakeChatModel`。它不是模型，只用固定规则把上下文边界变成可重复测试的行为：同样问“那还能直接取消吗？”，不带历史时缺少订单信息，带历史时才能关联订单 A1001 的发货状态。

完整代码位于 [`examples/chapter01_agent_basics`](https://github.com/MIRS571/java-backend-to-agent/tree/main/examples/chapter01_agent_basics)。

在仓库根目录运行：

```powershell
uv run python -m examples.chapter01_agent_basics.main
```

关键调用是：

```python
without_history = ask(model, follow_up)
with_history = ask(model, follow_up, history)
```

两次调用使用同一个 `model` 对象，但结果不同的原因不是对象内部产生了记忆，而是第二次调用的 `messages` 明确包含了历史。

## 6. 关键 API 解释

本章暂不绑定具体 SDK，先理解模型接口中经常出现的字段：

| 字段或对象 | 输入 | 输出或影响 | 注意事项 |
| --- | --- | --- | --- |
| `model` | 模型标识 | 决定能力、速度、价格和可用功能 | 不同模型不能假设行为完全相同 |
| `messages` / `input` | 当前请求可见内容 | 构成主要上下文 | 不是无限长度，也不自动等于全部聊天记录 |
| `instructions` | 应用级指令 | 约束模型行为与输出 | 不是鉴权机制，仍可能被错误理解 |
| `previous_response_id` / conversation | 服务端状态引用 | 连接多轮请求 | 数据保留、成本和指令继承规则必须查文档 |
| `max_output_tokens` | 输出上限 | 限制生成长度与部分成本 | 过小可能截断，过大不代表答案更好 |
| 模型响应 | 消息、工具调用、状态、用量等 | 供应用继续处理 | 不应只假设响应永远是一段字符串 |

第 3 章会使用 LangChain 统一不同模型客户端的常用调用方式；第 4 章再处理 Structured Output 和 Tool Calling。

## 7. Java / Spring 类比

可以把一次模型调用粗略类比为：

```text
Controller -> Application Service -> LLM Client -> 外部模型服务
```

- Message 类似一个带 `role` 和 `content` 的请求 DTO；
- 模型 SDK 类似封装 HTTP、鉴权、序列化和超时的 Client；
- 组装上下文类似 Application Service 构造下游请求；
- 校验模型输出类似校验第三方接口响应。

类比到这里就应停止：普通 REST 服务通常按确定规则返回业务结果，而 LLM 是概率式生成系统。即使参数相同，也不应把输出稳定性等同于普通 Java 方法，更不能让模型绕过 Spring Security、领域校验或数据库事务。

## 8. Demo 与企业级写法

| 当前 Demo | 企业级系统需要补充 |
| --- | --- |
| 固定规则的 Fake Model | 真实 SDK、连接池、超时、限流、重试与错误映射 |
| 手动传递完整历史 | 会话存储、上下文裁剪、摘要、隐私和数据保留策略 |
| 一段字符串输出 | 结构化校验、证据引用、拒答与降级策略 |
| 无工具调用 | 工具白名单、参数校验、授权、幂等和审计 |
| 单次本地运行 | 评估集、指标、调用追踪、成本与延迟监控 |

企业项目中，身份和 `tenant_id` 应由可信网关或认证上下文注入，不能让模型从用户文本中自行判断。高风险写操作应当由确定性业务服务执行，必要时加入人工审批。

## 9. 局限性与常见错误

### 9.1 把流畅回答当成事实

模型擅长生成合理文本，也可能生成不存在的订单状态、政策或引用。解决方向不是要求模型“更认真”，而是通过工具或 RAG 提供证据，再由程序校验关键结果。

### 9.2 把聊天窗口误认为模型永久记忆

界面能连续对话，通常是应用重新发送历史、引用服务端会话状态或组合两者。更换会话、裁剪历史或超过上下文容量后，可见信息会发生变化。

### 9.3 把 Prompt 当作安全边界

“不允许退款”写进指令，只是行为约束，不是权限系统。用户输入和外部文档还可能包含 Prompt Injection。真正的权限检查必须在工具或业务服务中执行。

### 9.4 不设停止条件就构建 Agent

工具循环可能反复调用、增加费用，甚至重复产生副作用。生产 Agent 必须限制轮数、工具权限、超时和重试次数，并为高风险动作设置审批点。

### 9.5 一开始就使用复杂框架

框架能统一接口和编排流程，但也会隐藏真实数据流。先理解请求、上下文、输出和应用控制权，再学习 LangChain 与 LangGraph，后续排错会更直接。

## 10. 本章总结

- LLM 根据当前可见上下文生成候选输出；LLM API 是应用访问模型的接口。
- Message 是带角色的输入或输出项；Context 是本轮模型可见信息的集合。
- 多轮对话状态需要应用显式传递或引用，不能理解为模型天然永久记忆。
- Agent 不等于一次模型调用；它包含工具、状态、控制循环和安全边界。
- 模型不能授予权限，也不能替代业务数据库、事务和确定性校验。
- 简单模型调用能解决问题时，不应为了名称或流行度强行上 Agent。
